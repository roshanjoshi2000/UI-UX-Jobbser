Conventions & naming traps

Naming trap: job_posts = job listings on the map. jobs = hire ledger rows written when a company hires a worker for a listing. Almost every other table’s job_id means job_posts.id.
  • Workers vs companies: Workers are people looking for work; companies post and hire. Subscription take-homes are company-only (workers stay free).
  • user_id in applications, skills, education, etc. usually means workers.id.
  • Polymorphic columns: addresses.entity_type / entity_id; notifications.notifiable_*; devices.devicable_* (company or worker).
  • Payments today: Job activation is tracked on job_posts.paid + active (Stripe Checkout). There is no subscription table yet — that is a design gap for interview tasks.
  • Sanitization: Password / token columns are listed so you know they exist. Treat values as secrets; never invent real tokens in submissions.

Key relationships

  • companies 1→N job_posts (company_id)
  • job_posts 1→N applications (job_id)
  • workers 1→N applications (user_id)
  • companies N↔N workers via connections
  • Hire event → row in jobs (workerId, jobId=post, companyId)
  • companies + workers → message_threads → messages
  • Share token: referral_links (global per sharer); per-job connected-worker metrics: job_metrics
  • Successful referral attribution: referrals / pending external: open_referrals
  • Company team-join token: invite_links (not job share)
  • Location: addresses for company, worker, or job post via entity_type

Gaps useful for interview tasks

  • No subscription / plan / entitlement tables — greenfield for Backend task 1.
  • No first-class Stripe subscription ids — today pay-per-job via job_posts.paid / active (+ vouchers).
  • Reporting — compose from applications, job_posts, jobs (hires), job_metrics, referral_links, connections, notifications.
