Environments & workloads

Jobbser is not a single process. On AWS, containerized backends run under Amazon ECS (Fargate-compatible task definitions in our current setup).

EnvironmentIntentNotes
Prod Live API + real-time hub serving the mobile apps Always-on baseline; primary cost focus
Dev Non-production cluster for engineering Has existed as a second cluster; keeping it always-on has been expensive — designs that make Dev cheaper / on-demand are highly valued
TEST (aspirational) Like-for-like with Prod for release checks Not assumed fully built — see take-home Task 3

Main workloads on ECS

  • Jobbser-Api — ASP.NET Core REST API (jobs, applications, auth, payments hooks, notifications orchestration, S3/SES/Secrets clients).
  • JobbserMsgHub — dedicated real-time notification / refresh service that clients and the API talk to for live updates (separate deployable from the API).
Naming example (illustrative): task families such as jobbser-prd-api and jobbsermsghub-prd, images from ECR in eu-west-1, CloudWatch log groups per service, awsvpc networking, Fargate CPU/memory in the small tier (e.g. 256 CPU / 512 MB class).

AWS services we use

Service Role in Jobbser What usually drives cost / risk
Amazon ECS Orchestrates API + MsgHub containers (Dev/Prod shaped clusters). Always-on tasks, over-provisioned CPU/memory, duplicate non-prod baseline.
Amazon EC2 (where used for capacity) Historically / optionally backs cluster capacity alongside Fargate bill lines. Instance right-sizing, idle capacity, On-Demand mix, attached EBS.
Amazon ECR Container images for API and MsgHub. Image retention / unused tags (usually small vs compute).
Elastic Load Balancing (ALB) HTTPS entry to API / hub services. ALB hours (often a large fixed monthly slice).
Amazon VPC Private networking for tasks, DB, NAT where needed. NAT Gateway hours/data; public IPv4 charges.
Amazon RDS (MySQL) Primary transactional database (see DB schema pack). Instance class, storage, single-AZ vs Multi-AZ, backups.
Amazon S3 Profile images and uploaded assets. Storage growth, lifecycle, request/transfer volume.
Amazon SES Transactional / account / notification email. Send volume, bounce/complaint hygiene.
AWS Secrets Manager Runtime config: DB connection, JWT, Stripe, Firebase, hub endpoint, AWS-related settings. Secret count, retrieval frequency, env duplication.
CloudWatch Logs Container logs for API and MsgHub. Retention; noisy logging (usually secondary).
IAM roles Task / execution roles for ECS pulling images and reading secrets. Least privilege; no long-lived keys in app images.

Compute detail (ECS)

  • Launch type / compatibility: Fargate-compatible task definitions (requiresCompatibilities: FARGATE, networkMode: awsvpc).
  • Typical task size (Prod examples): on the order of 0.25 vCPU / 0.5 GB RAM per service task — treat as a starting point, not a hard rule.
  • Secrets injection: task definition can pull a Secrets Manager ARN into an env var (e.g. secret location) at start — values never belong in the take-home repo.
  • Logging: awslogs driver → per-service log group / stream prefix.
Terraform / GH Actions take-homes should sketch modules and workflow files in your own GitHub repo. They do not need to deploy for real.

Data, assets, email, secrets

RDS / MySQL

Application schema is documented separately in JOBBSER_DB_SCHEMA.html. Bill snapshots have used a small instance class (e.g. db.t4g.micro-class, single-AZ) — exact class can change; design for a managed MySQL that Prod and a future TEST each own separately.

S3

Object storage for logos, gallery images, and similar uploads from the API.

SES

Outbound email for verification, account, and product notification flows.

Secrets Manager

Bundles runtime configuration the API loads at start (connection string, JWT, Stripe, Firebase, hub URL, etc.). Prefer one secret (or a small set) per environment rather than scattering credentials in task env plaintext.

Networking & load balancing

  • ALB — public HTTPS front door to container services.
  • VPC — tasks in awsvpc; outbound often via NAT when private subnets are used.
  • Public IPv4 — can be a material line item when many addresses stay allocated.
  • DNS — API and hub hostnames point at the load-balanced front ends (exact hostnames not required for take-homes).

Cost reality (context for designs)

A real monthly snapshot (order-of-magnitude; numbers change) put most spend in EC2/NAT + public IPv4 + ECS/Fargate + ALB, with RDS comparatively small. Dev being always-on was painful enough that Dev has been switched off at times.

For take-homes: prefer designs that shrink always-on footprint, avoid duplicate full clusters without a plan, and keep TEST like-for-like without blindly doubling Prod cost.

Useful gaps for take-homes

  • Terraform: infra is historically managed operationally; a clean modules + envs + Actions layout is greenfield design work.
  • TEST: like-for-like Prod shape with its own DB and a justified data strategy is an open design problem.
  • Observability / IaC maturity: dashboards, Lambdas, and a dedicated Terraform repo are growth areas called out in intern role materials.
